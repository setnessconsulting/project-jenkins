# Portfolio onboarding and fork-safety model

This document defines the direction for expanding the centrally managed Jenkins service across Setness Consulting repositories. It is an architecture and onboarding contract, not evidence that additional repositories or fork pull requests are currently enabled.

## Portfolio direction

- Maintain one centrally managed Jenkins controller and one centrally trusted pipeline implementation, with an explicit, reviewed profile for each repository and workflow lane. Keep repository profiles in a separate private configuration repository; profiles are validated data, never executable pipeline code.
- Prefer one GitHub App installation over repository-specific SSH deploy keys. Install the App only on repositories being onboarded. A single App private key is held by the Jenkins controller; it is never copied to an agent or exposed to repository code.
- Scope short-lived installation tokens to one repository and the minimum permission needed for each operation. Keep check publication on the controller and separate from checkout. The Branch Source plugin's repository/permission strategies apply to untrusted credential use, not trusted organization scans or branch indexing; the latter may use the full installation permissions. Do not treat those strategy settings as proof of operation-scoped tokens. Verify the actual token permissions and runtime boundary for the pinned plugin version, and use a controller-side token broker or equivalent if the plugin cannot provide the required single-repository, least-permission tokens for each operation.
- Do not make one broad, long-lived credential available to all builds. If the chosen Jenkins checkout path cannot demonstrate a contents-read-only, repository-limited token that is removed before untrusted code starts, stop and use a token-free source-transfer design or retain the repository's existing CI gate until a safe implementation is proven.
- Keep repository identity, profile values, URLs, and secret material out of this public repository. Store operational profile data in a protected controller-side configuration source and validate it against a schema before job creation.
- Load only the private catalog's reviewed default-branch snapshot. Reject unrecognized profile IDs, executable fields, duplicate repository/workflow identities, and any profile change that lacks its profile-level and repository-level qualification evidence. Catalog data may select a reviewed implementation; it may not supply commands, scripts, shell fragments, Jenkinsfiles, or arbitrary agent labels.

GitHub supports installation access tokens restricted to selected repositories and a subset of the App's granted permissions; tokens expire after one hour. The exact token permissions and repositories must be read back and verified, not inferred from the credential's Jenkins UI strategy. See [GitHub App installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation) and [Jenkins GitHub App credential security notes](https://github.com/jenkinsci/github-branch-source-plugin/blob/master/docs/github-app.adoc).

## Fork and outside-contributor pull requests

Fork PRs are an eventual supported verification path so eligible outside contributions can merge under the repository's normal rules. A maintainer must apply the `jenkins-verify` label to opt a PR into Jenkins; an unlabeled fork PR must never receive a passing result. The label does not replace isolation. Fork builds remain disabled for a repository until its untrusted execution boundary passes qualification, including evidence that a per-run sandbox is stronger than a shared-kernel Docker container.

For fork PRs:

1. Build only a centrally trusted pipeline version. Never load or evaluate the PR's Jenkinsfile, pipeline definition, job configuration, or scripts before the trusted policy decides what may run.
2. Resolve the base repository, PR number, base SHA, fork owner/repository, and head SHA from trusted GitHub/Branch Source metadata. Confirm the run is for the configured repository and publish any check only to the verified head SHA.
3. Do not expose the App private key, Checks-write credential/token, checkout credential, production secret, persistent controller state, host mount, or Docker socket to the build process. Check publication is a controller-side operation.
4. Use a disposable, resource-limited worker with a clean workspace and no credentials when tests execute. Prefer a source-transfer flow that does not leave a checkout token in the worker. If checkout needs a short-lived read token, restrict it to that repository and contents-read, remove/revoke it before any PR-controlled command, and prove it is absent from process environment, Git config, temporary files, logs, and workspace before tests start. Restrict worker egress to reviewed dependency/test endpoints and deny access to the host, controller, private network, and cloud metadata services.
5. Test fork-controlled build scripts as hostile input: attempt credential/environment discovery, access to neighboring jobs/workspaces, controller and host access, network exfiltration, workspace persistence, and cancellation/cleanup. A denied or unsafe run must not become a passing required check.
6. Keep the existing authoritative CI required until fork runs have exact-head-SHA and App-attribution evidence, failure/cancellation behavior, cleanup, recovery, fallback, and branch-rule readback. Never bypass protection to merge an outside PR that Jenkins could not safely verify.

Jenkins documents that credentials can be exposed to malicious pull-request code if they are bound around steps that execute PR-controlled files. Its GitHub App documentation also distinguishes trusted scans from untrusted build contexts: repository/permission restrictions do not constrain scans or branch indexing, where tokens can retain the installation's permissions. Keep that threat model explicit; Jenkinsfile trust policy by itself does not make test commands in a PR trustworthy. See [Jenkins multibranch credential security](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) and the [GitHub App credential security notes](https://github.com/jenkinsci/github-branch-source-plugin/blob/master/docs/github-app.adoc).

## Repository rollout and AI-tool behavior

- Onboard repositories one at a time or in small workflow-homogeneous batches. Inventory PR, main-push, scheduled, manual, release, deployment, and maintenance triggers separately; map each verification lane to a centrally trusted profile. Do not infer workflow equivalence from repository names or copy a profile without review. Repos with no current verification workflow receive a meaningful baseline gate or a documented no-verification exception, not an invented passing check.
- Keep Actions authoritative until each repository's exact-SHA shadow matrix, isolation, cleanup, recovery, owner-controlled fallback, and branch-protection requirements pass. Cutover is explicit per repository; deployments remain separate and manual unless approved in a separate project.
- Qualify each shared pipeline/security profile with ten distinct exact-SHA cases, then require at least three representative exact-SHA cases for every repository, including its failure and specialized-lane behavior. Qualify every distinct scheduled/manual lane at least once. Keep Actions authoritative until each repository meets its own gates.
- Track progress primarily as Jenkins-owned, exact-SHA verification results divided by all routine eligible verification executions, grouped by repository, workflow lane, and trigger. Report fallback and intentionally retained Actions lanes separately. Actions minutes are secondary context, not the rollout success metric.
- Add repository-local agent guidance during onboarding (for example, `AGENTS.md` for Codex/OpenCode/Cursor and the tool-specific equivalent where used). It must state the repo's current authoritative gate, actual Jenkins check name, supported triggers, fallback path, deployment boundary, and fork policy. Start from [the repository agent-instructions template](repository-agent-instructions.template.md); do not copy a global claim that Jenkins is authoritative into a repo before that repo's cutover.
- AI tools authoring or reviewing PRs must refresh the live PR head and checks, identify the authoritative gate, and report Jenkins check source/App attribution and exact SHA when Jenkins is qualified. A green shadow check is informative, not merge approval. Review tools must not launch routine Actions runs after cutover; use only the documented owner-controlled fallback when appropriate.

## Current boundary

The existing first and optional second profiles remain separate shadow definitions. Their current owner/author restrictions and repository-specific SSH checkout credentials are not broadened by this document. No fork PR is newly enabled, no credential is rotated, and no branch protection or GitHub Actions workflow is changed by adding this architecture guidance.
